## Findings

- Vite tooling is present and working, but is currently a compatibility shell around the existing IIFE/classic-script app.
- `package.json` remains `commonjs`; this is correct for now.
- `index.html` loads 31 local classic scripts, 1 module script (`db.js`), and 2 inline scripts.
- `db.js` is native ESM internally but still exposes `window.DB` and has asynchronous readiness semantics.
- Extracted frontend modules are `window.XekhoApp.*` IIFE modules, not ESM exports.
- Backend and scripts remain CommonJS and should not be converted during frontend ESM migration.
- `app.js` remains the main blocker: ~11.9K lines, ~397 functions, heavy `window`/DOM/global-state coupling.

## Decision

Do not do one-shot ESM conversion.

Recommended next sprint is Phase E1 only:

- Add non-invasive `app/esm/main.js` compatibility harness.
- Add `scripts/verify-esm-entry.js`.
- Load ESM entry after existing classic scripts.
- Keep all `window.XekhoApp.*` compatibility globals.
- Keep root `package.json` as `commonjs`.

## Remaining risks

- Inline handlers and global functions can break if converted to ESM prematurely.
- `db.js` module timing must be abstracted behind an adapter before ESM consumers import data APIs.
- Cloud Functions/backend scripts should remain CommonJS until a separate backend migration plan exists.
